## Sellers and accepted deals

- Project sellers choose a project/category and, for an allotted plot, an eligible block and plot. Title, address, area and project pictures are derived on the server. They do not enter a listing title, address, conversion or image URL. The Pine projects retain the supplied block and plot ranges.
- Sellers enter one bid interval. The three bidding amounts add one, two or three times that interval to the current price.
- Auction facts, auction terms, negotiation terms and optional descriptions use numbered inputs. Focus starts `1.` and Enter creates the next item. Selected salient features and descriptions appear on listings; empty values and labels are omitted.
- Custom listings have plot number, optional block and sector, scheme, Kanal/Marla/square-foot area inputs, construction status, land-use category and an additional category field for Others. Sellers upload up to five pictures and choose the display picture. The listing gallery has previous/next arrows.
- Project and custom listings accept up to ten private supporting documents. Pictures accept JPEG, PNG and WebP up to 5 MB each; documents accept PDF or pictures up to 10 MB each. Files are validated server-side and stored in R2. Private documents are accessible only to their owner and signed-in authorized staff. An unpublished image is not public until referenced by an active project or approved listing.
- Staff can send review notes requesting changes or documents. Sellers see the note in My Listings and can edit and resubmit pending or rejected listings. Published auction facts and price intervals cannot be edited silently.
- Sellers can confirm enabling a green “Enter Negotiation with Seller” action in My Listings. Direct negotiation requires separate terms acceptance and available participation funds where a deposit is configured. Only one private negotiation can be active per listing.
- A seller can accept the latest auction bid, and either party can accept an offer addressed to them in negotiation. Acceptance creates one immutable closed-deal snapshot, closes the listing and notifies both parties to visit the office for documentation. Closed deals appear in My Account → My Deals. Losing bidders are notified, and their participation reservations are released atomically.
- Google-linked accounts have no password-change controls; the settings API also rejects attempts to set a password for those accounts. Customer accounts—including `muhammadfaisalinayat@gmail.com`—do not grant administrator permissions. The legacy customer-admin allowlist is no longer an authorization source.

## Balances, notifications and external configuration

Cash balances and participation reservations use integer paisa. Available balance equals total balance minus reservations. Configured project deposits apply to the seller at approval and to the bidder at participation. A zero deposit means no balance reservation is required. Users can see receipts, refunds and reservations under Account balance. Reserved amounts cannot be refunded as available cash. Refund entries record money actually returned; they do not send a payment automatically. Unresolved balances and accepted-deal documentation block account deletion.

The existing reviewed-deal fees, participation-payment, settlement and payout ledger remains separate. Its financial regression suite still passes. This update does not enable PayFast or invent a completed online payment.

Every persistent customer notification has a durable email-outbox record. Delivery requires the existing `RESEND_API_KEY` and `EMAIL_FROM` settings with an authorized sender. Failed requests remain queued and retry with backoff and provider idempotency keys. Missing credentials are reported as queued delivery; no successful send is claimed. Worker POST requests schedule delivery, and a five-minute cron retries pending mail and maintains expired negotiations/reservations. Provider acceptance is distinct from confirmed inbox delivery.

The site uses a new R2 binding named `BUCKET`, targeting `auctionhouse-uploads`. R2 must be enabled and the bucket created in the same Cloudflare account before deployment. Do not make the bucket publicly accessible; the application serves authorized files itself.

## Release steps

1. Back up the current production D1 database using the existing documented procedure.
2. From `deployment/`, authenticate to the correct Cloudflare account. If R2 is not yet enabled, enable it for that account. Create the private bucket once:

   ```powershell
   npx.cmd --no-install wrangler r2 bucket create auctionhouse-uploads
   ```

   Skip creation if that bucket already exists. Do not create another D1 database or Worker.

3. Preserve the existing `PII_ENCRYPTION_KEY`, Google settings and email-provider secrets. Configure the email sender if it is not already connected.
4. Run `npm.cmd run database`. It applies all pending migrations, including `0003_plain_stature.sql`, `0004_fat_valeria_richards.sql` and `0005_curved_sheva_callister.sql`. Earlier migrations remain unchanged.
5. Run `npm.cmd run check`, then `npm.cmd run deploy` when ready to publish.
6. Sign in at `/budapest-admin` and complete the mandatory initial password change. Review project facts/terms, plot inventories, deposit amounts, home placement, staff roles and contact details.
7. Verify a customer favourite, a confirmed demo bid, a real seller submission/review, private document access, negotiation, the notifications inbox and a delivered test email. Real Google sign-in and email delivery require provider-configured testing.

No GitHub CI/CD troubleshooting or automatic deployment was resumed by this task.
